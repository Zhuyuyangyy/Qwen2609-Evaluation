### Dimension Details

#### D1. Novelty / Technical Contribution -- 7.0/10

Strengths:
- The behavior-graph modeling of multi-agent tool-call chains is a legitimate and under-explored angle in the agent safety literature.
- Risk propagation with decay across the behavior graph, combined with downstream amplification detection, provides a structural signal that single-call guardrails cannot capture.
- The what-if counterfactual branch projection is a useful analytical construct.
- The MCP protocol-level attack detection module (tool poisoning, rug-pull, shadow server) addresses a real and recent attack surface.

Weaknesses:
- The core engine (`v3_engine.py`) does not actually compute risk. It receives `risk_score` as an external input and maps it to actions via a threshold function. The "intelligence" is entirely in `baselines.py`'s feature engineering, which is not integrated into the engine pipeline.
- The conformal prediction module (`cp/core.py`) is a well-known technique applied to a new domain; the novelty is incremental.

#### D2. Technical Soundness -- 5.0/10

**This is the weakest dimension and the primary barrier to Q2 acceptance.**

Critical Deficiency:
- **Label Leakage in V3 Standard Benchmark (evaluate_v3.py, line 32)**: The benchmark feeds the ground-truth `expected_risk_score` directly as `risk_score` into the V3 engine. This means the engine is evaluated on its ability to convert known scores to actions (a trivial threshold mapping), NOT on its ability to assess risk from tool calls. This completely invalidates the reported V3-standard benchmark accuracy figures.

Pipeline Disconnect:
- The `MCPAttackDetector` and `ToolDescriptionValidator` modules are fully implemented but never called from the `V3ShieldEngine.process_tool_call()` method or the API routes. They are orphaned code.
- The `V3ShieldEngine` is a passthrough: it accepts `risk_score` from the caller and applies `_action_for_score()`. There is no internal risk assessment logic. The actual risk scoring intelligence lives in `baselines.py::risk_agent_shield_graph()`, which is never wired into the engine.

Risk Propagation Issues:
- `compute_risk_propagation()` uses a simple max-based backward BFS. The decay factor `1/(1 + 0.3*chain_length)` is ad-hoc and not theoretically grounded. No sensitivity analysis or ablation on the decay parameter is reported.
- The `get_critical_nodes()` method requires `downstream_risk_amplified=True`, which is only set when `inherited > 0.1` -- a magic threshold with no justification.

#### D3. Experimental Rigor -- 4.0/10

Critical Issues:
- The V3-standard benchmark (`evaluate_v3.py`) has label leakage as described above. Reported numbers are meaningless.
- The SCI-600 and semi-real baselines (`baselines.py`) correctly avoid label leakage by inferring risk from observable features. However, the "AgentShield + Graph" baseline constructs a single-node graph per case with a synthetic downstream proxy node -- this is not how real multi-step chains work.
- No cross-validation or train/test split is used for the SCI-600 dataset. All 600 cases are evaluated on the same set.
- The ablation study removes components that contribute 0-2% accuracy, except for "special-case rules" which contribute ~24%. This suggests the system's performance is dominated by hand-crafted heuristics, not the graph or chain reasoning.
- No statistical significance tests (e.g., McNemar's test, bootstrap confidence intervals) are reported.

## 2. Top 3 Must-Fix Issues (Priority Order)

### ISSUE-1 [CRITICAL]: Label Leakage in evaluate_v3.py

**File**: `benchmark/evaluate_v3.py`, line 32
**Problem**: The benchmark passes `case["expected_risk_score"]` (ground truth) as `risk_score` to the V3 engine. This means the engine receives the answer before making a decision. The reported "Score Acc" and "Action Acc" metrics are measuring trivial score-to-action mapping, not risk assessment capability.
**Impact**: All V3-standard benchmark results are invalid. This is a fatal flaw for any SCI submission.
**Fix**: The benchmark must use the same risk scoring pipeline as `baselines.py` (i.e., `risk_agent_shield_graph()`) to compute risk scores from observable features, then pass those to the engine.

### ISSUE-2 [HIGH]: MCP Detector/Validator Not Integrated into V3 Engine Pipeline

**Files**: `backend/app/shield/v3_engine.py`, `backend/app/api/routes.py`
**Problem**: `MCPAttackDetector` and `ToolDescriptionValidator` are fully implemented with 100+ test cases but never called from the main `process_tool_call()` pipeline. They are orphaned modules.
**Impact**: The protocol-level security capabilities (rug-pull, shadow server, description injection) are not exercised in any end-to-end flow. A reviewer testing the API will see no evidence of MCP security.
**Fix**: Integrate `MCPAttackDetector.analyze_tool_call()` into `V3ShieldEngine.process_tool_call()` and merge the `MCPThreatReport.threat_score` into the final risk score.

### ISSUE-3 [HIGH]: V3 Engine Is a Risk-Score Passthrough

**File**: `backend/app/shield/v3_engine.py`
**Problem**: The engine's `process_tool_call()` accepts `risk_score` as an external parameter. It does not compute risk internally. The actual risk intelligence is in `baselines.py::risk_agent_shield_graph()`, which is never wired into the engine. The engine is effectively a graph builder + threshold mapper.
**Impact**: The engine cannot be used as a standalone governance system. Any caller must compute risk externally, which defeats the purpose of a "shield engine."
**Fix**: Wire `risk_agent_shield_graph()` (or a configurable risk scoring function) into the engine as the default risk computation, making the external `risk_score` parameter optional.

## 3. Immediate Fix: ISSUE-1 -- Label Leakage in evaluate_v3.py

The most critical issue is the label leakage. Below is the fix applied to `evaluate_v3.py`:

### Root Cause
```python
# BEFORE (line 32): Ground truth leaked into the engine
result = engine.process_tool_call(
    ...
    risk_score=expected_risk,  # <-- THIS IS THE LABEL
    ...
)
```

### Fix Applied
The benchmark now uses the same observable-feature-based risk scoring as `baselines.py`, specifically `risk_agent_shield_graph()`, which does NOT read ground-truth fields. The engine receives a computed risk score derived from tool names, inputs, and category priors -- the same information available at inference time.

### Additional Changes
1. Added `risk_agent_shield_graph` import from `baselines.py`
2. Replaced `expected_risk` with `risk_agent_shield_graph(case)` in the evaluation
3. Updated the score delta computation to compare computed vs expected
4. Added a fairness note to the output
